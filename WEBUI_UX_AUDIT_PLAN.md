# Agent Wasp whole-app Web UI/UX and API audit plan

**Audit baseline:** `binqqarenyu-whole-app-ux-audit-plan`, `6530e7bdd73ad3bfa6ab8ed0f6724338920b97e1`

**Scope:** Read-only source, route, documentation, test, and local route-registry review. This document is a plan and evidence record; it does not implement a redesign or prescribe deleting code.

## 1. Executive conclusion

**Recommendation: targeted redesign of the shared shell and highest-value operator journeys, not a wholesale WebUI rewrite. Confidence: moderate.** The app already has a coherent server-rendered foundation: `create_app` registers the dashboard routers, Jinja templates share `base.html`, static CSS/JavaScript are served locally, and the tested page families are backed by explicit route modules. Replacing that architecture without evidence of user pain would add risk without a demonstrated benefit.

There is, however, evidence for a focused UX and reliability pass: theme selection is reset to dark on every page load; the persistent “connected/live” strip displays fixed account and service claims rather than visibly bound status; navigation and documentation disagree about pages and route counts; and the source scan found no explicit skip link, current-page navigation semantics, or reduced-motion rule. The largest uncertainty is whether the current hierarchy and density actually impede operators: this repository contains no user research, deployment telemetry, or accessible live dashboard to answer that. Phase 0 therefore establishes real workflows and usage before deciding whether any portion needs broader redesign.

**Do not delete backend endpoints solely because a current template does not call them.** No backend route was confirmed dead in this audit. Preserve routes until in-repository and out-of-repository consumers, compatibility expectations, and runtime evidence (if available) have been checked. The “orphan candidates” below are leads, not deletion decisions.

## 2. Application map

```mermaid
flowchart LR
    U[Operator browser] --> A[FastAPI create_app]
    A --> M[Auth and security middleware]
    A --> R[34 dashboard route modules]
    A --> S[/static CSS, JS, images]
    R --> T[Jinja templates and shared base]
    T --> J[Page JS: fetch, SSE, HTMX]
    J --> R
    R --> D[DB, Redis, event bus]
    R --> W[Models, skills, scheduler, integrations]
    X[CLI scripts and documented operator API] --> R
    Y[Telegram service] --> Z[Agent/runtime services]
```

- `containers/agent-core/src/dashboard/app.py:58-98` creates the FastAPI app, installs `AuthMiddleware` and per-request security headers, configures Jinja, and mounts `/static`. `app.py:101-179` imports and mounts the dashboard routers with prefixes; page handlers receive shared services from `app.state`.
- The server-rendered UI comprises **35 template names returned by `TemplateResponse`** (including login/register and detail/visual surfaces), with shared layout in `templates/base.html` and reusable Jinja macros in `templates/macros.html`. The template directory also contains `base.html` itself. `base.html` is a 1,021-line shell containing responsive drawer markup, navigation, global controls, shared dialogs, and substantial JavaScript; page-specific behavior/styles are frequently inline in templates.
- Local assets are `static/css/tailwind.css`, `static/style.css`, `static/app.js`, and locally served libraries under `static/js/` (`htmx`, `marked`, and `d3`). `tailwind-build/package.json` defines the CSS build/watch scripts. The main shell loads local HTMX, application JS, and Marked; the workspace graph loads D3.
- Interaction patterns include ordinary form posts, page-level `fetch`, a chat SSE stream (`chat.html:1180`), a live-feed stream (`live.html:381`), and an HTMX-generated state fragment (`routes/state.py:188`). Repository searches also found CLI/operator-script and test consumers of dashboard routes; Telegram is a separate service/interface, not evidence that an unreferenced dashboard route is unused.
- The runtime route registry was instantiated locally without starting a server or connecting to services: it contained **178 Starlette routes**, including the `/static` mount and default `/openapi.json`; its registered HTTP methods totalled **179**. A source scan counted **176 route decorators across the 34 imported router modules**. These counts use different units and are not directly comparable to the documentation’s “151 HTTP endpoints”; reconcile them with a generated method/path manifest in Phase 0.

The brain, visual graph, badge, SSE streams, and macros have direct consumers. The local SVG integration logos are selected from a mapping in `integrations.html`, so a simple “not a literal `<img>` in every page” search would be misleading.

## 4. Prioritized findings

| Priority | Finding | Evidence, confidence, counter-evidence, and risk |
|---|---|---|
| P1 | Theme preference is overwritten on every page load. | **Verified, high confidence:** `base.html:20-24` unconditionally sets `wasp-theme` and the document theme to `wasp-dark`; `toggleTheme()` later stores the selected value at `base.html:29-35`. Since links cause new document requests, a light selection is not preserved across navigation/reload. **Risk:** visible control promises persistence it does not deliver. No browser reproduction was available; the conclusion follows directly from the initialization code. |
| P1 | Always-visible connected-service strip presents fixed “LIVE/ONLINE” claims. | **Verified markup, high confidence:** `base.html:350-368` hard-codes an account label, Gmail “Integrated & Working,” and Windows Host “Active & Connected”; repo search found no runtime binding for these cards. The separate workflow ribbon is hidden until state logic updates it (`base.html:1053-1065`), which is counter-evidence that dynamic state is already used elsewhere. **Risk:** operators can mistake design/demo text for live health. Verify intent and available health source before changing semantics. |
| P1 | Current route documentation and some route-count claims are out of sync. | **Verified, high confidence:** `dashboard.md` claims 151 endpoints and five sidebar sections (`:4,11`), but `base.html` labels six sections (`:188,212,235,242,285,300`). Docs list `/cmd`, `/opportunities`, `/state`, and `/auth/logout` (`dashboard.md:15,29,75-76`), while current routes mount `/api/commands`, opportunity APIs only, state utilities only, and `GET /logout` (`app.py:144,175,179`; `cmd.py:9`; `opportunities.py:21,59,90`; `auth_routes.py:158`). The source/runtime counts are method/decorator/route-object counts and need one canonical generator before replacing the prose “151.” **Risk:** broken operator expectations and misleading smoke checks. |
| P2 | Navigation hierarchy and accessibility need task-based validation before a redesign decision. | **Source scan, moderate confidence:** the shared shell has six categories and many destinations (`base.html:188-321`), while active links are styled by path; no explicit `<nav>`, `aria-current`, skip link, or `prefers-reduced-motion`/`focus-visible` rule was found in the HTML and `style.css` search. The shell does have a responsive drawer, `main`, and labels on some controls (`base.html:77-81,160,382-385`), and form focus styling exists (`style.css:702-710`). **Risk:** keyboard/screen-reader wayfinding and motion preferences may be inconsistent. A source search is not a WCAG audit; test actual pages before asserting conformance failures. |
| P2 | Current tests protect selected API/UI-adjacent behavior, not end-to-end page quality. | **Verified, high confidence:** `tests/test_mesh_cockpit_atse.py`, `test_self_improve_atse.py`, and `test_workspaces_and_subagents_ui.py` are API-level `TestClient` tests. No dashboard browser E2E harness was present in `tests/`, despite `Makefile` documenting `test-e2e` against `tests/e2e_harness/`. **Counter-evidence:** the repository has a standalone `audit_routes.py` and other route tests, so there is some smoke/API coverage. **Risk:** navigation, responsive, keyboard, loading/error states, and route/API drift can regress without detection. |
| P3 | Several large surfaces and the shell concentrate behavior/styles. | **Verified structure, moderate confidence:** `base.html` is 1,021 lines; large pages such as `mesh_cockpit.html` contain their own extensive inline behavior. This is a maintainability signal, not proof of poor UX. **Counter-evidence:** the current server-rendered architecture and common macros are usable; avoid a framework migration unless baseline work demonstrates it is needed. |
| P3 | A small set of API-only routes merit consumer mapping, not immediate deletion. | **Static search finding, medium/low confidence:** command palette API and chat/cognitive/model utility handlers have no direct page call found; opportunities and metrics APIs have explicit documentation, and agent/goal/mesh endpoints have script/test consumers. **Risk:** “no direct template reference” is not equivalent to “unused”; accidental removal could break scripts or deployed integrations. |

### Dependency and context-preservation rules

- Phase 0 inventory and observation can be parallelized; Phase 1 decisions depend on both. Phase 2 is gated by signed-off IA/interaction scope. Phase 3 page families may be implemented in parallel only after the shared shell contract is stable and changes do not collide in `base.html`; merge/test them serially.
- Backend retirement is a separate, owner-approved sequence. Page/API work can keep existing endpoints while UX is improved. Never combine a speculative endpoint deletion with a broad UI redesign.

## 6. Risks, assumptions, and open questions

- **No deployment evidence:** no live instance, access logs, product analytics, user interviews, support tickets, or telemetry snapshots were available. Repository code proves declared routes and wiring, not real usage, visual quality in a browser, or performance.
- **No browser audit:** the application was not launched and `audit_routes.py` was not run against a service. Its own target is a locally configured host/port; running it would measure an environment not established as representative.
- **No external consumers known:** public/operator docs and tracked scripts/tests are partial evidence. Private scripts and downstream clients are unknown. Treat unreferenced APIs as compatibility risk until runtime/owner review.
- **Design assumptions:** operators may need desktop-first density for health/forensics and mobile-friendly controls for basic response; neither target nor priority is evidenced. Confirm before reducing density or moving controls.
- **Status semantics:** the fixed connected-service strip may be mock/demo content or a real-status claim; source code alone does not establish intent. Verify the desired product behavior and actual data source.
- **Scope risk:** a new SPA/framework or large visual refresh could increase maintenance, CSP, routing, and deployment risk. There is no evidence here requiring such a migration.
- **Open decisions:** which operators/roles are in scope; top three daily journeys; whether command palette and opportunity page are intended; support window for operator API compatibility; target mobile/tablet/browser support; acceptable accessibility target; availability of production logs; and whether a minimal browser test dependency is acceptable if the current repository cannot run a UI suite.
